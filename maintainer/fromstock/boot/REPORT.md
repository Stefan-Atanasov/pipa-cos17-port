# pipa base-port beta4 boot pieces: stock/public source hunt (offline, 2026-11-19)
Evidence: evidence/ (node lists, md5 lists, avbtool dump, TWRP props), fw-md5.tsv, carried-sources.tsv.
Big extractions deleted. Nothing was flashed or tested.

## 1. boot.img (beta4 / hi9)
- Header v3, os_version 16.0.0, patch 2099-12, empty cmdline. Ramdisk gzip cpio, 82 MB unpacked, 990 files. Our hi9 boot has the byte-identical ramdisk (only the kernel differs).
- It is TWRP: system/bin/twrp, twres, twrp.flags, strings "3.7.1_16-16.0". prop.default: name twrp_pipa, device pipa, Xiaomi Pad 6, Android 16 (BP2A.250605.031.A2), eng/test-keys, built "Mon Oct 5 13:37:01 UTC 2026", ro.build.user=root, host=ubuntu, incremental eng.root.
- Conclusion: a SELF-BUILT TWRP (twrp-16.0 minimal manifest, own device tree) by the port author, build host "ubuntu". Matches beta4 kernel built by joeyzhu@ubuntu on 17 Oct. No public pipa TWRP 3.7.1_16 found by web search (twrp.me has no pipa page; only TWRP 3.7.1_16 builds for other devices, e.g. popsicle). Source = UNKNOWN (author's private device tree). twrp.flags/fstab are readable in evidence/ and are enough to recreate a device tree (fstab: f2fs /data with wrappedkey, dynamic partitions system/system_ext/product/vendor/odm/mi_ext, by-name/rescue as /cache).
- Beta4 kernel in it: 4.19.325-cip136-st20-N0-kernel++ (joeyzhu@ubuntu, clang 20.1.8, #8, 17 Oct 2026). Ours: walt-hi9 (stefan@pipa-cos17, AOSP clang 20, 18 Nov).
- PixelOS boot.img alternative: header v3, os 17.0.0, patch 2026-07, empty cmdline, gzip ramdisk 1.5 MB = plain first-stage init ramdisk (init, system/etc only), NOT recovery. Format-wise our kernel can be repacked into it (same header v3, same layout; use mkboot.sh, never magiskboot -h). It would boot Android via vendor_boot (PixelOS vendor_boot is a Lineage recovery/first-stage). But it carries no TWRP: recovery then is only the vendor_boot Lineage recovery. Untested.

## 2. vendor_boot.img
- Header v3, pagesize 4096, dtb_offset 0x1f00000, cmdline: androidboot.hardware=qcom androidboot.console=ttyMSM0 androidboot.memcg=1 lpm_levels.sleep_disabled=1 msm_rtb.filter=0x237 service_locator.enable=1 androidboot.usbcontroller=a600000.dwc3 swiotlb=2048 loop.max_part=7 cgroup.memory=nokmem,nosocket reboot=panic_warm androidboot.fstab_suffix=qcom androidboot.init_fatal_reboot_target=recovery buildvariant=user androidboot.init_fatal_panic=true androidboot.boot_timeout=1800 androidboot.selinux=enforcing ignore_loglevel
- PixelOS cmdline is the same up to init_fatal_reboot_target=recovery; beta4 appends buildvariant=user, init_fatal_panic, boot_timeout=1800, selinux=enforcing, ignore_loglevel (author edits).
- Vendor ramdisk: Lineage-style recovery ramdisk (lineage_pipa, ro.lineage.device=pipa, fingerprint google/mustang_beta ... Aug 22 2026, build.user android-build, flavor pipa-user, A17 CP2A.260605.016), 393 files. vs PixelOS vendor ramdisk (403 files, custom_pipa userdebug, ci@PixelOS-CI, 5 Aug 2026): 232 files identical, 160 differ (binaries: init, adbd, fastbootd, libs, fstab), 1 only beta4, 11 only PixelOS. Recovery fstab: erofs system/system_ext/product (PixelOS: ext4). iqraOS vendor_boot ramdisk is only 2 KB (no recovery) and a different dtb.
- DTB: 3 dtbs (kona v2.1/v2/v1). Decompiled with dtc. Node set vs PixelOS dtb: beta4 lacks only `qcom,ion-heap@20` (CAMERA) and bootargs has extra `noirqdebug`; otherwise identical node/compat set (4082 vs 4084 nodes/props in my reduced list). Vs our tree (out/.../kona-v2.1.dtb, 26471 dts lines): ours has +756 nodes, all coresight/debug (funnel, cti, tpdm, tpda, etm, tmc, replicator, stm); beta4 has none of them; ion-heap CAMERA and our bootargs (no noirqdebug) are in ours. Our dtb equals iqraOS dtb except iqraOS still has mem-offline (our tree deleted it, liyafe commit c8434c20).
- Conclusion: beta4 dtb = same kona/liyafe/Lineage-24 source family as our tree, but built WITHOUT kona-coresight.dtsi, without kona-ion CAMERA heap, plus `noirqdebug`. PixelOS has the same coresight-less shape. Exact source = unknown build of a similar tree; reproducible by editing our tree: drop `#include "kona-coresight.dtsi"` (kona.dtsi:5207), drop heap@20, append noirqdebug (untested; value of these differences unknown, hi9 already runs fine with beta4 dtb). Safest plan: keep the beta4 vendor_boot as a binary blob, or take PixelOS vendor_boot and re-apply the cmdline.

## 3. dtbo.img
- Beta4: 13 entries (alioth apollo cas cmi dagu elish enuma lmi munch pipa psyche thyme umi), 33 MB padded, table v0, all ids 0. PixelOS dtbo: 13 entries, 12 non-pipa entries md5-IDENTICAL to beta4; pipa entry differs by 114 bytes: beta4 has extra `fragment@165 target=<&msm_gpu> qcom,min-pwrlevel=<0>`. Stock OS1.0.15 and iqraOS dtbo: 29 entries (all kona SKUs), different.
- Our tree out/arch/arm64/boot/dtbo.img: 1 entry (pipa only, 731666 B vs beta4 pipa 722915); differs in fragment numbering and lacks the min-pwrlevel fragment.
- Conclusion: beta4 dtbo = PixelOS-style (Lineage multi-device build) dtbo with a GPU min-pwrlevel=0 patch on the pipa entry. Our own tree can build the pipa overlay but not the 13-entry image; the 12 other entries are irrelevant for pipa (kernel picks by board id/msm-id; verify id match). Source: PixelOS dtbo + 1 patch. UNKNOWN exact source tree; a one-entry dtbo from our tree is untested (needs test; the dtbo.img is also hashed into vbmeta, but flags 3 ignore it).

## 4. Firmware (fw-md5.tsv)

Only abl differs; dtbo, vbmeta, vbmeta_system, vendor_boot are the port author's. boot absent in iqraOS firmware-update.
- Versions: xbl BOOT.XF.3.2-00304-SM8250-2, OEM pangu-build-bp-104924-wff76-6x9zh-qp6vf; tz/hyp TZ.XF.5.8-00226; aop AOP.HO.2.0-00187; modem MPSS.HI.2.0.c7 (strings). Stock OS1.0.15: same QC strings, OEM pangu-build-bp-47990-..., different md5 for all except dsp (dsp.img IDENTICAL to stock OS1.0.15).
- abl: beta4 vs iqraOS both signed ELF (cert dated 2025-04-27; OS1.0.15 abl cert 2024-12-09), same segment layout, 41819 bytes differ from 0x1108 to 0x2b2c5 = hash table AND payload, so not signature-only: a different (or patched) abl build. Beta4 abl is not in any stock set I have. Could not name it.
- Which official release: web: xmfirmwareupdater.com lists pipa China OS1.0.4 ... OS2.0.8 / OS2.0.11 / OS2.0.12.0.UMZCNXM (fastboot, ~6.4 GB; 2025-08). The exact release matching bp-104924 is NOT determined (needs one fastboot ROM downloaded and md5 compared). iqraOS CN 3.0.303 is not documented online. Since the 17 images equal iqraOS, taking /mnt/reference/pipa/iqraOS3.1.../firmware-update is already a stock-derived source.

## 5. vbmeta
- beta4 vbmeta.img: avbtool 1.4.0, SHA256_RSA4096, signed with the AOSP TEST key (pubkey sha1 2597c218...), rollback 0, flags 3 (verity+verification disabled), chain descriptor vbmeta_system (loc 1), hash descriptors boot/dtbo/vendor_boot + hashtree odm/vendor (stale, from the Lineage pipa build; ignored with flags 3). Props: lineage_pipa A17 CP2A.260605.016 fingerprints.
- vbmeta_system.img: same test key, rollback 1785542400, flags 0, hashtree descriptors for product/system/system_ext of the author's A17 build (stale). Ignored because the top vbmeta has flags 3.
- iqraOS vbmeta: Xiaomi key b2a02f1e..., RSA2048, flags 3; stock OS1.0.15 flags 0.
- Rebuild is easy: `avbtool make_vbmeta_image --flags 3 --padding_size 4096 --output vbmeta.img` and an empty-descriptor vbmeta_system (or `fastboot --disable-verity --disable-verification flash vbmeta stock_vbmeta.img`, which sets flags 3 in a stock vbmeta; stock vbmeta chain still points at vbmeta_system signed by the Xiaomi key, so vbmeta_system must then also be a valid stock one or rollback index must be <= stock). The rollback index 1785542400 of beta4 vbmeta_system could block a later flash of lower values only if the device stores it (not on unlocked sm8250 with avb 1.0 rollback index off? UNKNOWN). TEST needed.

## 6. Carried system files (carried-sources.tsv, 34 rows)

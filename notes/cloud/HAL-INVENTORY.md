# HAL inventory: vendor.oplus.hardware.* interfaces called by the ColorOS 17 donor system side

Static notes (cloud session, 2026-11-03). Reviewed against the donor files. Nothing here is tested on a device.

- **Donor build:** OPPO Pad Mini OPD2515, OTA `OPD2515_11.C.07_1070_202610201803`, ColorOS 17.0.0.104(CN01).
- **Port donor:** the port documents C.06. C.07 is the newest build that the OTA server offers. It is a bug-fix release.
  Where I could compare, C.07 equals C.06: the C.07 `surfaceflinger` has md5 `405ff9632578c15c6b36ef795cb0853b`, the same
  as `STOCK_MD5` in `module/tools/patch_sf_waits.py`. The C.07 Java jars (`services.jar`, `oplus-services.jar`, `framework.jar`,
  `oplus-framework.jar`) have new md5 values. Re-apply every jar patch of the port on C.07 before use.
- **Date:** 2026-11-03.
- **Method:** static only. String scan of all partitions (826 files with hits), VINTF and service-context files,
  androguard disassembly of selected classes, ELF import and call-site checks. No device, no adb.

## Summary

- 82 `vendor.oplus.hardware.*` HAL packages are named in the C.07 framework VINTF files. The odm VINTF set declares 31 of them.
- Status on pipa: 5 PRESENT, 5 SHIMMED (4 from the task list plus `displaycolorfeature`, which step 2x also covers), about 70 MISSING (28 rows below).
- The one HIGH item is `displaypanelfeature`. Its interface has only 3 methods.
- Three vendor APEX files carry HALs: `vendor.oplus.hardware.engineer.aidl.apex`, `vendor.oplus.hardware.stability.aidl.apex` and
  `vendor.oplus.hmbird.apex` (a library only).
- Four interfaces run in the other direction: the framework serves them and the vendor side calls them
  (`osense.client`, `commondcs`, `hummingbird`, and partly `urcc`). Their absence on pipa costs nothing.
- Blocking waits: see the list below. Two new items need a check on a device: the `getService(true)` fallback for `misc`, and
  `libsensorserviceextimpl.so` waiting for `oplusSensor`.

"Donor provides" means the C.07 vendor, odm or vendor APEX. "Callers" count only system-side files (system, system_ext,
product, my_*). Interface libraries, permission XML, `.map` files and `oat/` files are not callers.

## MISSING, by impact

1. **displaypanelfeature (HIGH).** SurfaceFlinger, `services.jar`, `oplus-services.jar` and OplusGames use it for idle refresh, Game Filter and
   adaptive colour. The port already works around three uses (2z, 3f, 3s). The interface has 3 methods, so a stub service is cheap.
   The mapping of the feature ids to pipa display controls is the real work.
2. **gameopt (MED).** Game frame hints for SurfaceFlinger and `oiface`. Small interface (14 methods). A no-op stub is realistic.
   It gives a gain only with the OPPO kernel parts that pipa lacks.
3. **misc (MED, hang risk).** Five methods. A stub also removes the `getService(true)` fallback (see the list below; probably no hang on pipa, see the note there). Best cost-benefit of all MISSING items.
4. **oplusSensor (MED).** Nine methods. `libsensorserviceextimpl.so` waits for it. The port already reroutes sensor types (2w).
5. **cwb (LOW-MED).** Frame read-back for display features and the screen monitor. A defaults stub is possible. Real data is not.
6. **virtual_device.audio / virtual_device.camera.manager (LOW-MED).** Interconnect audio and camera. Possible link to call sharing audio (BUGS item 27). Not verified.
7. **urcc, transmessage, location, rpmh, handlefactory, orms, binaural_record / a2dp_offload (LOW).** No tablet feature is clearly lost.
   `transmessage` and `urcc` each have a blocking wait. Both are cheap to stub.
8. **engineer, riskdetect, olc2, osense.client, commondcs, hummingbird, pogo_keyboard, diagnostics group (NONE-LOW).**
   Factory, diagnostics or framework-served. `engineer` is already patched out.
9. **NONE on a Wi-Fi tablet:** radio, ims, appradio, esim, satellite, nfc, nfcExtns, felica, eid, secure_element, fingerprint, fingerprintpay, camera family, biometrics.face.

## Blocking waits found

A wait is dangerous on pipa when the service is not registered and the call has no time limit. Java `waitForDeclaredService` returns null
at once if no VINTF file declares the name (standard `ServiceManager` code: it calls `isDeclared` first; I did not re-check this in the C.07 framework.jar). It is not listed as blocking.
Plain `waitForService` (Java or NDK) blocks. HIDL `getService(true)` blocks only when the device VINTF manifest declares that HIDL instance: for an undeclared instance hwservicemanager answers at once with null. pipa does not declare `vendor.oplus.hardware.misc@1.0` (not in the PRESENT list), so the two `misc` rows below are probably no hang. Confirm on the device.

## Method

1. `scan.py` collected every `vendor.oplus.hardware.*` string from dex (apk, jar), ELF, XML, rc and map files. Result: `scan.json`, 826 files.
2. VINTF: read all manifest and compatibility files under odm, vendor, system, system_ext and product (82 package names in the matrices, 31 in odm manifests, 5 in the system manifest). Service contexts: vendor, odm.
3. Donor provider: matched odm `etc/init/*.rc`, `odm/bin/hw/*` and the vendor APEX payloads (strings of the VINTF and rc text only; no files were extracted).
4. Features: from package, class and method names, and from the method lists of the AIDL interface classes. Method names and transaction counts come from the disassembly of the interface jars.
5. Blocking waits: byte scan of every hit file for `waitForService` / `waitForDeclaredService`; then androguard per method to find which OPPO name each Java wait uses; `llvm-objdump` call-site scan of each native file that imports `AServiceManager_waitForService`, with the next `fromBinder` call as the type marker; a scan of the oplus-services and services disassembly for HIDL `getService(Z)`.
6. Repo cross-check: `grep` for each interface in the port repo (steps, notes, sepolicy, docs).

Tools and temporary output stayed in the cloud work folder (not in git). No code is pasted in this file. No binary was copied.
